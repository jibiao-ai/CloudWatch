# 资源拓扑「怎么显示才不乱」调研与原型设计

> 状态：**方案已确认并落地开发**（5 项决策见 `docs/DEVLOG.md` 第54轮）。本文保留为调研与设计依据。
> 调研对象：生产环境 `/topology`（北京生产环境），调研日期 2026-10-05。
> 原型：[`prototype.html`](./prototype.html)（单文件，双击浏览器即可打开；数据为生产结构快照，IP 已脱敏）。

## 1. 现状诊断（基于生产实测）

### 1.1 数据规模（北京生产环境，单平台）

| 类型 | 总数 | 异常/告警 | 关系（边） |
|---|---|---|---|
| 物理节点 | 45 | 异常 11 / 告警 26 | phys→host 37 |
| 计算节点 | 37 | 异常 2 / 告警 16 | host→vm 382 |
| 虚拟机 | 382 | 异常 16 / 告警 5 / 停止 40 | vm→volume 601，vm→port 124 |
| 云硬盘 | 982 | 异常 14 / 告警 18 | volume→pool 980 |
| 虚拟网卡 | 125 | 停止 8 | port→network 125 |
| 集群存储 / 网络 | 3 / 21 | 存储池异常 1 | — |
| **合计** | **1595 节点 / 2249 边** | 接口返回 1.2 MB | |

结构特征（决定了方案选择）：

- **本质是一棵树**：物理 →(1:1)→ 计算 →(平均 10.6，最大 20)→ 虚拟机 →(平均 1.66，最大 6)→ 云硬盘/网卡。
- **只有两类“枢纽”会让连线爆炸**：存储池（3 个，入边 387 / 593）与网络（21 个，入边最多 23）。980 条 volume→pool 的线是画成节点连线图后“一团乱麻”的根源。
- **381 块云硬盘未挂载任何虚拟机**（占 39%），在分层图里是漂浮的孤点。
- **问题只占少数**：异常/告警的虚拟机仅 21 台，分布在 16 台宿主机上 —— 用户真正关心的是“哪里有问题”。

### 1.2 现有页面的 6 个“乱”点

| # | 现象 | 根因 | 影响 |
|---|---|---|---|
| 1 | 全部展开后页面约 **40,437 px** 高 | 5 层卡片平铺，982 块云硬盘/382 台虚拟机一次性渲染 | 滚动一个多屏看不到头，无整体感 |
| 2 | 看不出谁属于谁 | 各层是平铺列表，父子关系只能靠点击高亮；图例写了“虚线”，实际页面没有任何连线 | 拓扑名不副实 |
| 3 | **“45 + 37 异常” 被读成 “4537”** | 总数粗体与“N 异常”红字紧挨着，缺少分隔与语义 | 数字误读 |
| 4 | 红色泛滥 | 物理节点 37/45 异常 + 计算节点异常，异常率口径过宽，整屏红色，失去“预警”意义 | 找不到真正严重的问题 |
| 5 | 角标数字无标签 | 告警条数角标与“14 台云主机”靠近且不带单位 | 混淆 |
| 6 | 字体小且密 | 每个 Chip 同时塞名称、IP、状态点、角标 | 阅读吃力 |

## 2. 设计原则（6 条）

1. **先看结论再看明细**：默认回答“哪里有问题”，正常资源降饱和（浅绿弱化）。
2. **嵌套代替分层**：用“包含关系”表达 物理 → 计算 → 虚拟机，父子一眼可读，**不靠连线**。
3. **连线按需出现**：仅在选中一台虚拟机时画它的 **1 跳** 关系线（≤ 15 条），全程不出现全量连线。
4. **枢纽节点汇聚**：存储池/网络作为顶部“汇聚带”，点击后**反向高亮**受影响的虚拟机，而不是拉出上千条线。
5. **数字有语义**：总数与状态拆开展示，配**堆叠状态条**（异常/告警/停止/正常），数字必带单位与标签。
6. **逐级下钻**：平台 → 宿主机 → 虚拟机，面包屑可回退，任一屏 ≤ 60 个块。

## 3. 方案对比

| 维度 | A. 分层泳道 + 按需连线 | **B. 嵌套热力块 + 汇聚带 + 按需 1 跳图（推荐）** | C. 力导向/全量节点连线图 |
|---|---|---|---|
| 表达方式 | 5 条横向泳道，节点为卡片 | 宿主机卡片内嵌“虚拟机方块”，顶部汇聚存储池/网络 | 自由布局的节点 + 全部连线 |
| 单屏元素量（本数据） | 1595（需虚拟滚动） | **≈ 37 张卡 + 382 个方块（首屏）** | 1595 点 + 2249 线 |
| 父子关系可读性 | 中（需连线辅助） | **高（包含即归属）** | 低（线交叉） |
| 发现问题的速度 | 中 | **高（异常置顶、红块一眼可见）** | 低 |
| 枢纽节点处理 | 连线汇聚到同一点，仍密 | **聚合成汇聚带 + 反向高亮** | 严重“毛球” |
| 实现成本 | 中（需 SVG 连线 + 虚拟滚动） | **中低（纯 DOM/CSS + 1 张小 SVG，不引入图库）** | 高（需 d3-force/cytoscape，包体积 + 性能） |
| 随规模增长 | 一般 | **好（按宿主机分页/分组）** | 差（>500 节点即不可读） |
| 风险 | 线仍多 | 对“跨宿主机”的横向关系表达弱 → 用反向高亮补足 | 不可控 |

**结论：采用 B 为主体**，借鉴 A 的“按需连线”（仅在虚拟机详情里出现），**不推荐 C**（该数据量下必乱，且需引入新依赖）。

## 4. 推荐方案的信息架构与交互

```
一级：平台总览（多平台卡片，沿用现有 Overview，仅修正数字展示）
二级：平台视图（本原型主屏）
   ├─ KPI 状态条 ×7：类型 + 总数(带“个”) + 堆叠状态条 + 异常/告警/停止拆分
   ├─ 汇聚带：集群存储(3，含使用率条) ｜ 网络(21，按网卡数排序，Top8 + “更多”)
   ├─ 宿主机热力块：异常优先排序；卡片内每个方块=1 台虚拟机，颜色=健康度
   ├─ 仅物理角色节点（无计算服务）：紧凑 chip 列表
   ├─ 未挂载云硬盘（381）：默认折叠，分页加载，不污染主拓扑
   └─ 右栏：待处理问题（严重优先，点击直达）+ 选中对象详情
三级：宿主机视图（下钻）
   ├─ 宿主机摘要（物理节点状态、CPU/内存、异常/停止统计）
   ├─ 虚拟机卡片网格（异常优先）
   └─ 选中虚拟机 → 底部“关系图”：物理 → 计算 → 虚拟机 → 云硬盘/网卡 → 存储池/网络（仅 1 跳）
```

### 4.1 交互规格

| 操作 | 行为 |
|---|---|
| 点击宿主机卡片 | 下钻至宿主机视图，面包屑出现 `平台 › node-80` |
| 点击热力方块 | 直达该虚拟机（宿主机视图并选中，展开关系图） |
| 悬停方块 | Tooltip：名称 / IP / 状态 |
| 点击存储池/网络 | 其余宿主机淡化，被关联虚拟机保持高亮；顶部显示“关联 N 台虚拟机”条，可一键清除 |
| 筛选“仅异常/告警” | 宿主机、虚拟机列表同步过滤 |
| 搜索 | 命中宿主机/虚拟机/IP；方块以描边高亮 |
| 右栏问题列表 | 点击跳到对应宿主机/虚拟机（存储池则触发反向高亮） |
| 关系图 | 虚拟机最多展示 7 块云硬盘 + 7 个网卡，超出显示“+N”并引导到右侧详情 |

### 4.2 视觉规范（遵循项目铁律）

- 颜色只用主题变量（`--c-danger/--c-warning/--c-success`…），**正常状态用 30% 透明度的弱绿**，异常/告警保持满饱和 → 红/橙只在真正需要关注处出现。
- **卡片左侧 4px 色条**表示最严重状态，取代整卡红底，减少“满屏红”。
- 状态标签用**文字 + 圆点**，不只靠颜色（色弱友好）。
- 禁止毛玻璃、禁止原生 select；图标走 lucide（原型因单文件省略）。

### 4.3 “4537”问题的修正

| 现状 | 修正 |
|---|---|
| `物理节点 45` + `37 异常`（紧挨） | `物理节点 **45 个**` ＋ 堆叠条 ＋ `● 异常 11  ● 告警 26` |
| 异常口径：异常+告警混计 | 拆分“异常 / 告警 / 停止”三档，各自带圆点与标签 |
| 角标无标签 | 标签统一为“N 台虚拟机异常”“N 停止”等带单位文案 |

## 5. 对数据与接口的影响（开发阶段再评估）

当前 `GET /api/topology/{providerId}` 一次返回 1.2 MB 全量。推荐方案**首期可不改后端**（前端直接用现有 nodes/edges 建索引：`host→vm`、`vm→volume/port`、`volume→pool`、`port→network`），但规模再翻倍后建议：

1. **精简字段**：列表只带 `id/name/health/type/parent`，`attrs/reasons` 等详情按需 `GET /api/topology/{pid}/node/{id}`。
2. **服务端预聚合**：返回每个宿主机的 `{vmTotal, danger, warning, off}` 与存储池/网络的 `vmCount`，前端不再遍历边。
3. **孤儿云硬盘**独立分页接口 `GET /api/topology/{pid}/orphans?page=`。
4. 压缩（gzip 已有则忽略）+ 缓存 30–60 秒。

## 6. 性能策略

- 首屏仅渲染 37 张宿主机卡 + 382 个方块（纯 DOM，< 1k 节点）；云硬盘/网卡**从不整体渲染**，只在虚拟机下钻后出现（≤ 14 个）。
- 未挂载云硬盘折叠 + 分页（每次 24 条）。
- 宿主机 > 100 台时：按物理机房/集群分组折叠，或引入虚拟滚动。
- 关系图用单个 `<svg>` + 贝塞尔曲线，不引入图库（保持包体积不变）。

## 8. 风险与待确认问题

1. **“异常”口径**：目前物理节点 37/45 为异常，疑似阈值/规则过宽（如“内存 ≥85%”“隧道连通故障”均计入）。建议产品确认：拓扑只展示 **严重(critical) = 异常**，warning = 告警，避免满屏红。
2. **跨宿主机关系**（如同一存储池、同一网络的所有虚拟机）靠“反向高亮”表达，是否满足“看连线”的预期？如必须有全局连线，可加“显示关系线”开关，仅对选中对象开启。
3. **多平台**：总览页是否需要跨平台汇总的热力图？（原型只覆盖单平台视图。）
4. **宿主机数量增长**到 200+ 时的分组维度（机房/AZ/集群）数据是否可获得？
5. 未挂载云硬盘 381 块（39%）：是正常的闲置资源还是需治理的“僵尸盘”？可作为后续“成本/治理”入口。

## 9. 原型使用说明

打开 `prototype.html`：

1. 默认进入平台视图：异常宿主机在最前，方块红色=异常虚拟机。
2. 点击顶部 **hdd** 存储池 → 观察反向高亮（258 台虚拟机关联，其余淡化）；再点一次或“清除”恢复。
3. 点击任一宿主机卡片 → 下钻；点击虚拟机卡片 → 底部出现关系图、右栏出现详情。
4. 右侧“待处理问题”点击可直达；顶部“仅异常/告警”、搜索可联动。
5. 面包屑点击“北京生产环境”返回。
